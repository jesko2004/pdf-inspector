# PDF/RAG 后端当前版本验收方案

日期：2026-09-10。本文为验收方案；实际执行状态以 `acceptance-report.md` 为准。

本轮范围已按用户要求改为**离线本地验收**：本地 PDF 解析、RapidOCR、SQLite、任务与知识库状态、权限、恢复和流式协议。使用 hash Embedding 与 extractive LLM，无需模型 API 或外部模型服务。已关闭原指定审查项 1、2、4、5、10，并按 6 → 3 → 7 → 8 → 9 顺序完成可执行审查。最终结果与未关闭内容问题见报告，不自动扩大实施范围。

## 1. 验收范围与结论边界

验收对象为单实例 PDF/RAG 后端：PDF 上传、持久化任务、字段与表格提取、OCR、Chunk、知识库生命周期、检索、引用问答，以及基础权限、监控和备份恢复。

当前 [交付范围与已知限制](acceptance-scope.md) 已同步后续修复：Q-04 已知封面案例在受限本地 RapidOCR 路径通过；通用图像文字完整补全仍不作保证，`ready` 不证明全部可见文字完整。显示问题只有在不影响关键值、单位、字段含义、正文语义或来源关系时才可暂缓。下文检查标准应在该明确范围内执行，不能据此豁免实质语义错误。

当前版本不纳入 BM25 混合检索、多租户隔离、分布式任务队列、对象存储。这四项标为“暂缓”，不作为当前版本验收失败条件。验收中暴露的实际问题应先分析原因，不直接扩展这四项功能。

默认采用 SQLite 向量存储。只有目标部署选择 pgvector 时才执行其真实连接、重启和备份恢复验收。FlashRank 只有启用时才纳入运行及效果验收。扫描件识别若列为当前交付能力，就必须完成真实 OCR 验收；未安装依赖不能计为通过。

验收边界：

- 工程验收：允许使用本地 hash Embedding 和 extractive LLM，验证接口、状态与数据生命周期。
- 真实模型业务验收：不纳入本轮。下文的语义召回率、答案质量、模型费用和在线延迟门槛仅供未来启用真实模型时参考，不作为本轮未通过原因。离线替代 Provider 的通过结果不能证明真实模型质量。

## 2. 第一步：冻结版本与建立独立环境

1. 记录 `git rev-parse HEAD`、代码差异、操作系统、CPU/内存、Python/Rust 版本和依赖版本。
2. 使用工作区内独立数据目录，例如 `test_output/acceptance/data`；服务绑定 `127.0.0.1:8100`。记录脱敏后的 Provider、模型、向量维度、OCR、重排与限流配置。
3. 原始样本与测试输出保存在 `test_output/acceptance/`；不要把原始业务文件、密钥和未脱敏日志提交到 Git。
4. 明确设置 `PDF_INSPECTOR_EMBEDDING_PROVIDER=hash` 和 `PDF_INSPECTOR_LLM_PROVIDER=extractive`；OCR 使用本地模型文件。不得在本轮切换到外部模型或自动下载模型。
5. 不切换现有服务的数据目录；重启、失败注入、删除和恢复只在验收环境执行。

项目本地 Python 环境的启动示例（在仓库根目录运行，前台运行便于查看输出和停止）：

```powershell
$acceptancePython = 'F:\pdf inspector\.codex-tools\api-venv\Scripts\python.exe'
$env:PDF_INSPECTOR_DATA_DIR = 'F:\pdf inspector\test_output\acceptance\data'
$env:PDF_INSPECTOR_HOST = '127.0.0.1'
$env:PDF_INSPECTOR_PORT = '8100'
$env:PDF_INSPECTOR_EMBEDDING_PROVIDER = 'hash'
$env:PDF_INSPECTOR_LLM_PROVIDER = 'extractive'
& $acceptancePython -m uvicorn backend.app:create_app --factory --host 127.0.0.1 --port 8100
```

上例需要环境已安装后端依赖和原生 Python 扩展。OCR、服务访问用 API Key 等参数按 `docs/backend.md` 配置；不要把文档中的占位符直接作为有效配置。服务访问 Key 与模型 API Key 是两回事；本轮不需要模型 API Key。

通过标准：`GET /health` 正常；可以打开 `http://127.0.0.1:8100/docs`；记录明确的版本与运行配置。

## 3. 第二步：准备小型真实验收集

建议先准备 12 份可合法用于测试的 PDF：

| 类别 | 数量 | 检查重点 |
|---|---:|---|
| 普通中文正文 | 3 | 标题、段落、页码、引用 |
| 报价单或参数表 | 3 | 型号、数量、金额、表头与行对应 |
| 英文或中英混排 | 2 | 字体编码、关键词、章节 |
| 纯扫描件 | 2 | 真实 OCR 与置信度记录 |
| 正文与扫描页混合 | 1 | 仅补全目标页、保留原始页序 |
| 长文档或复杂多栏 | 1 | 阅读顺序、父子 Chunk、上下文预算 |

另外准备一份非 PDF 文件和一份损坏 PDF 作为异常样本，独立统计，不混入正常提取成功率。

人工建立 30 个问题及标准证据：20 个有答案问题、10 个无答案问题。有答案问题覆盖正文、型号/金额、跨页、表格以及改写表达；标注标准答案要点、文件名、PDF 实际页码和证据原文。先完成标注，再查看系统答案。页码按 PDF 文件第一页为 1，不按印刷页码。

普通文档使用合适的业务模板；不要把采购模板缺少供应商、金额等必填字段导致的 `needs_review` 当作解析失败。

## 5. 第四步：逐份验证 PDF 处理

通过 OpenAPI 页面依次调用：

1. `POST /v1/tasks` 上传 PDF，保存 task ID。
2. `GET /v1/tasks/{id}` 轮询到终态，记录耗时和状态。
3. `GET /v1/tasks/{id}/result` 保存完整结果。
4. `GET /v1/tasks/{id}/tables` 与表格 CSV 接口检查结构化输出。
5. `GET /v1/tasks/{id}/chunks` 检查 Chunk、页码、章节和质量信息。

逐份对照原 PDF，至少抽查首尾页、全部已标注证据页和关键表格。检查正文阅读顺序、金额/型号、表格行列、字段证据、OCR 页序和失败提示。

通过标准：

- 正常样本均产生可解释结果；非 PDF 和损坏文件被明确拒绝或记为失败，服务继续可用。
- 抽查的关键金额、数量和型号正确，或明确标记人工复核；不得把错误值当作已验证结果静默交付。
- 引用页码与源页对应；表格不串行、不串列；正文无影响理解的大段漏失或乱码。
- 扫描及混合样本实际完成 OCR；未识别页面保留失败信息和复核状态。
- `needs_review` 可以是正确行为，必须按原因人工判断，不能只统计 `ready` 比例。

## 6. 第五步：验证知识库生命周期

按下列顺序执行，保存 KB ID、document ID、Chunk 数与索引状态：

1. `POST /v1/knowledge-bases` 创建独立验收库。
2. `POST /v1/knowledge-bases/{id}/documents` 关联已完成任务；查询文档和批次直至索引结束。
3. 对同一任务重复入库，确认幂等响应且不产生重复有效文档/Chunk。
4. 用相同 `document_key` 更新一份修改过的文档，验证新内容可查、旧内容按版本策略处理。
5. 单独验证显式版本的历史/as-of 查询：默认引用有效版本，指定历史条件能找到历史来源。
6. 在专用测试 Provider 下模拟一个批次失败，再恢复 Provider 并重试；成功批次应保留，失败批次可恢复。不要通过破坏真实数据库或外部模型服务制造失败。
7. 最后删除专用测试文档，确认其 Chunk 和向量清理，检索不再返回该文档。

通过标准：无重复入库、无错误版本混用、无孤立检索结果；批次失败可解释且可重试。

## 7. 第六步：验证离线检索与问答协议

本轮执行接口响应、入库与查询关联、引用定位、空库拒答、SSE 正常/异常流程和上下文预算检查。下面的 Recall、MRR、答案正确率及复杂拒答质量门槛仅作为未来真实模型业务验收的参考。保留离线 hash 的实际测量值，不将其改记为语义质量达标。

### 检索

将 20 个有答案问题写入 `examples/retrieval_eval.sample.json` 相同结构的新文件，替换真实 document ID 和页码，调用：

`POST /v1/knowledge-bases/{id}/retrieval-evaluations`

固定模型、数据和 `top_k=5`，保存 Recall@5、MRR、每题来源、平均延迟和 P95。20 题的 P95 只作为初步观察；更稳定的延迟统计见第八步。

未来真实模型验收的建议门槛：平均 Recall@5 ≥ 0.90，MRR ≥ 0.80。它们是未来小规模业务验收的建议值，不是既有测量结果或行业承诺；应在正式执行前冻结。逐题检查失败案例，不能只看均值。

如启用查询改写或 FlashRank，用相同问题集调用 `compare_rewrite` / `compare_rerank` 比较开关前后的结果。接受标准为不丢失关键证据、Recall 不下降，且排序收益与增加的延迟相匹配；否则关闭该可选项即可。

### 问答与流式响应

对全部 30 题调用 `POST /v1/knowledge-bases/{id}/ask`：

- 20 个有答案问题：人工核对答案要点、实际使用的引用、文件/页码和表格关系。
- 10 个无答案问题：包含完全无关问题，以及主题相关但缺少所问细节的问题，检查是否明确拒答或说明证据不足。
- 选取至少 3 个有答案问题和 1 个拒答问题设置 `stream=true`，核对 `metadata → token → done` 或拒答流程；可控 Provider 异常应产生明确 `error`。
- 检查长上下文截断、父章节回填和重复上下文控制，确认预算和来源信息可解释。

未来真实模型验收的建议门槛：有答案问题至少 18/20 回答正确且证据充分；关键金额、型号与版本问题不得出现错误结论；全部已使用引用都能定位且支持相应结论。10 个无答案问题不得编造确定答案。

特别区分：现有“没有检索结果达到阈值时不调用 LLM”的拒答机制，不能证明“检索到了相关文字但答案不在其中”时也能正确拒答，后者必须用真实模型实测。无法仅从最终答案推断调用次数时，结合单元测试和 Provider 调用记录验证。

## 8. 第七步：验证权限、恢复和备份

1. 配置验收用 `read`、`write`、`admin` 三类 API Key；分别验证允许和禁止的操作。启用认证后，无 Key/错误 Key 不得访问受保护接口；只读 Key 不得写入，非管理员不得执行管理员操作。`/health` 和 OpenAPI 页面公开不算越权。
2. 降低验收环境的限流阈值并连续请求，确认超限返回 429，恢复窗口后可正常使用；观察 Request ID、审计和管理员指标接口。
3. 仅终止验收服务进程，在任务处理中重启同一数据目录，检查中断任务恢复、已完成结果仍可读取。
4. 待写入和索引结束后停止验收服务，执行一次静止数据备份；恢复到全新的空目录，再启动恢复实例。

```powershell
& $acceptancePython -m backend.backup create 'test_output/acceptance/data' 'test_output/acceptance/backup.tar.gz'
& $acceptancePython -m backend.backup verify 'test_output/acceptance/backup.tar.gz'
& $acceptancePython -m backend.backup restore 'test_output/acceptance/backup.tar.gz' 'test_output/acceptance/restored'
```

5. 恢复实例与备份前对比任务、知识库、文档和 Chunk 数，抽查结果文件，重复 5 个固定检索问题核对来源一致。生成模型答案措辞可以不同。

通过标准：权限边界生效；任务可恢复；备份校验通过且恢复后的数据可用。若选择 pgvector，以上本地归档不包含 PostgreSQL 外部数据，必须额外备份/恢复外部向量数据库，并联合验证元数据与向量一致性。

## 9. 第八步：做小规模稳定性验收

本轮仅建立本机离线基线；真实模型 Token 用量、在线延迟和生产 SLA 不适用。峰值内存必须采集实际服务进程；OCR 并发与关闭 OCR 的上传并发分开记录。未完成的测量不得记为通过。

在最终选定硬件和模型配置上执行至少 100 次检索、30 次问答和一轮样本上传；先单请求，再以 2～3 个并发请求观察。重复问题的延迟统计标明缓存和预热条件；FlashRank/OCR 首次模型加载与正常运行分别记录。

记录请求量、非预期 5xx、超时、P50/P95、SSE 首段 token 延迟、总耗时、峰值内存、队列排空时间及真实模型 Token 用量。单独区分预期限流和主动注入的故障。

通过标准：本轮无非预期崩溃、卡死、数据丢失或 5xx，所有正常任务最终完成或给出明确可处理错误。延迟应在测量前约定业务可接受上限；尚无响应时间要求时先形成基线，结论标记“性能基线已建立，SLA 未验收”，不臆定生产性能达标。
