## 推荐目标

交付一个在明确范围内可用、可复测、可解释失败的离线本地版本。完成本方案后，可判定“离线本地版本在约定范围内基本验收通过，保留已披露限制”；不宣称任意 PDF 完美提取、所有八步无条件通过或生产环境已验收。

范围保留：Rust PDF 提取、本地 RapidOCR、SQLite 单实例后端、已知发票模板、任务和知识库生命周期、离线检索引用协议、权限及备份恢复。hash/extractive 只证明工程链路，不证明真实模型回答质量。

不追加：BM25、多租户、分布式队列、对象存储、外部模型接入、完整手写识别、通用图像文字补全。现有通过项不重复开发。

## 第一阶段：关闭影响正文语义的三个问题

| 顺序 | 工作 | 最小实现边界 | 必须验证的结果 |
|---|---|---|---|
| 1 | Q-01 多栏串读 | 定位栏目判定与排序错误，按几何结构修正；不用样本文件名、固定词句或哈希硬编码 | 杂志第 1、11 页按栏连贯读取，不把不同栏拼成一句；参数表、发票及已有多栏样本无退化 |
| 2 | Q-02 侧边标题插入 | 保持侧栏标题独立，避免它改变正文分组；复用现有布局能力 | 清单第 1 页正文不被 Emergency Supply List 打断，第 2 页也无新增顺序问题 |
| 3 | Q-03 双语说明误判与符号 | 修正普通段落被判为表格的条件；检查复选框编码或表达 | 第 1 页说明连续且强调片段归属正确；第 48 页复选框不能继续作为货币符号 £ 静默输出 |

每项先形成可重现失败用例，再做最小修复，最后核对源页和定向回归。测试应覆盖相邻的正确版式，防止为一个样本破坏真实表格。只在人工核对后更新确属有意变化的快照。

如果不能可靠恢复某一字段或符号，可选择明确的“不确定/需人工复核”结果，并验证提示确实能传递到用户使用的接口或文档流程；仅在最终报告里写“请人工检查”，不能代替接口已经承诺的正确行为。不得把整份文档一律标成复核来规避验收，也不得根据测试样本名称绕过失败。

这三项如果仍存在静默语义错误，就不能宣布包含相应文档类型的基本验收通过。若后续决定排除某类文档，必须明确调整交付范围，并保留原失败记录；本方案没有自动作出该范围变更。

## 第二阶段：冻结可暂缓的限制

第二阶段完成时 Q-04 暂缓，随后应用户修复要求，其已知目录封面案例在本地 RapidOCR 后端通过。当前版本处理原生文字、已识别需要 OCR 的页面，并对符合条件的图片封面补充文字；仍不承诺在所有原生文字页面上发现并完整补全任意图像文字。原失败记录继续保留，不将受限修复扩写为通用完整识别。

在 README 的验证说明、后端使用说明和最终报告中统一这项边界。受限封面路径已有验证；超出该路径的品牌、标题或其他图像文字若作为业务证据，仍需复核源页或采用另行验证的处理方式，不能宣传为通用完整提取能力。

重复绘制标题和中文换行空格已有定向修复。其他暂缓项：非关键复杂表头及其他排版显示改善，以及手写/旋转印章完整识别。若其中某项实际改变本轮标注的金额、单位、字段含义或来源关系，就升级为必修，不能继续以“显示问题”暂缓。

发票 BSB 源文件冲突继续保持 needs_review，这一状态属于正确行为，不需要修改成 ready。

## 第三阶段：在最终候选上统一复测

1. 记录最终源码差异、依赖和产物哈希，重建实际用于验收的原生扩展与所需 CLI。源码或产物改变后，不再引用旧运行结果作为新候选直接通过的证据。
2. 每项修复期间只跑受影响检查；功能冻结后统一执行格式、严格 Clippy、Rust 测试、后端测试、Python 绑定和脚本测试。本轮修复后的参考数为 Rust 893、后端 95 通过/1 跳过、Python 64、脚本 17；新增回归后以实际数量为准。候选相关实现及产物未变化时可引用本轮已完成证据。
3. 重新处理现有 16 份、86 页覆盖集。核对全部已标注关键证据页、三个缺陷涉及页面以及首尾页；若改动影响中间页，也必须抽查受影响页。核对正文顺序、关键值、字段复核原因、表格行列及 OCR 页码，不只统计 ready。
4. 复测已知发票正反例和 CSV、Freon 数值单位与两栏顺序、混合文档仅第 2 页 OCR、跨页证据引用。冻结预期，不根据新输出倒改答案。
5. 用最终候选跑一次上传→结果→入库→检索引用的本地冒烟流程；从独立备份恢复后抽查结果可读、检索来源可用。已有详细权限、失败注入、恢复测试可以引用，在相关实现没有变化时不重复全量人工操作。
6. 保留此前 OCR 并发和内存基线，注明其候选与日期。此次若只改变布局算法，补正常/混合文档运行检查即可；若改变 OCR 路由、引擎、任务并发、缓存或出现耗时/内存异常，再重测并发和内存，不能把旧数字冒充新测量。

不要求补真实模型 API，也不增加线上部署、长时间压力测试或生产 SLA。pgvector 仍不选用时，保留有原因的跳过。

## 第四阶段：解决提交要求与可复现性

项目 [AGENTS.md](../AGENTS.md) 明确要求：`Run cargo build --release then bench.py test in that repo before committing.` 其中 that repo 指 pdf-evals。缺少该套件不阻止本地报告与 GitHub 文案准备，但按现行项目规则，不能直接跳过后提交。

后续优先核实维护者提供的兼容仓库来源及获取方式；允许联网且来源可用时，由执行者获取并运行，无需用户寻找离线副本。不猜测某个同名仓库就是正确套件。若来源不可得，则在其他工作和提交材料都准备好后，由项目负责人明确决定是否对本次提交豁免该要求；批准时在 PR 中记明套件未运行及本次替代证据。豁免只能改变交付条件，不能将未执行改记为通过。后续负责人已于 2026-09-10 明确回复“选择路径Ｂ收尾”，本次豁免生效，长期规则不变。

同时解决当前证据只在本机的问题：

- 将关键缺陷的最小复现与回归断言纳入可跟踪测试。适合的合成样本保留生成方法；源 PDF 只有确认允许再分发后才纳入仓库。不能依赖别人没有的 tests/local-fixtures 或 test_output 作为唯一复现路径。
- 整理可共享的环境、命令、结果摘要及哈希；原始大文件、独立测试数据库、访问密钥和无关简历 DOCX 不纳入提交。
- 核对新文档、模板、测试在 Git 中确实被包含，不能只提交 git diff 所显示的已跟踪文件，遗漏当前未跟踪的新文件。
- 发布原始 PDF 或完整日志之前检查其必要性和是否允许共享；对外报告不能只给别人无法访问的本机绝对路径。

## GitHub 正式交付顺序

1. 生成最终待提交文件清单，排除无关文件；记录测试和外部回归结论。
2. 根据最终差异重写标题与描述，使用 [GitHub 收尾草稿](github-closeout-draft.md) 作为起点。当前草稿只包含已发生事实，未来修复通过后再补入。
3. 明确目标分支和 PR 对比范围。若 PR 包含此前分支上的其他功能提交，必须审查整个分支差异并调整文案，不能只描述当前未提交修复。
4. 满足项目要求及相应提交/推送授权后，提交、推送并创建 PR。用户已要求按顺序完成；本次豁免已批准，继续执行；远程发布状态以实际操作结果为准。
5. 根据实际结果形成最终中文总结：交付内容、验收范围、测试结果、暂缓项、复现方法、提交或 PR 链接。只有实际创建后才写链接，未做的事项保留未执行。

最终交付物为：修复及回归测试、更新后的验收报告和问题清单、可复现验收材料、使用说明、GitHub 标题与描述、中文收尾总结。无需额外增加展示页面或无关功能。

外部套件的完整处置方案已补充，见 [pdf-evals 问题说明与解决方案](external-regression-resolution.md)。本次单次豁免已由负责人选择路径 B 明确批准；长期独立回归仍仅为建议。
