## 1. PDF-001：表格内容页缺少页面标记

- 发现时间：2026-09-06
- 修复时间：2026-09-06 16:30:47（Asia/Shanghai）
- 级别：高
- 状态：已关闭（实现完成并通过真实样本回归）
- 影响模块：`src/markdown/convert.rs`、表格输出与页面分组逻辑

### 现象

启用 `pdf2md --pages` 后，部分页面的内容已经写入 Markdown，但对应的 `<!-- Page N -->` 标记没有写入。

### 已确认样本

1. 第一批 `13-tax-return-form.pdf`：源文件共 2 页，第 2 页内容存在于一个大型 Markdown 表格中，但缺少 `<!-- Page 2 -->`。
2. 第二批 `02-full-product-catalogue.pdf`：源文件共 4 页，输出标记为 `1、2、4`；检测器确认第 3 页有表格，输出也包含该页商品表格，因此第 3 页不是空白页。

### 原因判断

表格可能通过独立于普通文本行的输出分支写入。页面标记由普通文本循环触发时，只有表格或者由跨页表格承载内容的页面不会触发标记。

### 解决方案

1. 将 Markdown 生成过程统一成“按源 PDF 页逐页输出”。
2. 每一页开始时先写页面标记，再写该页的表格、正文、图片提示等内容。
3. 表格检测结果应携带原始页码，跨页表格也要在页边界插入对应标记。
4. 避免由“该页是否存在普通 TextLine”决定是否写页面标记。

### 实际修复方法

1. 为 `merge_continuation_tables` 增加 `preserve_page_boundaries` 参数。
2. 当 `MarkdownOptions.include_page_numbers` 为 `true` 时，不再把后续表格页合并并删除，而是保留每一页的表格数据和原始页码。
3. 刷新位于两个正文页之间的 table-only/image-only 页面前，先输出该页的 `<!-- Page N -->` 标记。
4. 刷新最后一个正文页之后剩余的 table-only/image-only 页面时，同样先输出页面标记。
5. 未启用 `--pages` 时仍按原有逻辑合并跨页连续表格，避免改变默认 Markdown 输出策略。
6. 新增两个单元测试，分别验证中间表格页的标记顺序，以及启用页面标记时连续表格页不会被合并删除。

### 验收标准

1. 上述两份样本的标记序列分别严格为 `1,2` 和 `1,2,3,4`。
2. 每个标记只出现一次。
3. 修复后表格内容和阅读顺序不发生倒退。

### 修复结果

1. `13-tax-return-form.pdf`：修复前只有 `Page 1`，修复后标记严格为 `1,2`，42 行 Markdown 表格仍然保留。
2. `02-full-product-catalogue.pdf`：修复前标记为 `1,2,4`，修复后严格为 `1,2,3,4`，第 3 页商品表格仍然保留。
3. 两份样本的 `pdf2md` 退出码均为 0。
4. 不使用 `--pages` 再次转换报税表时，页面标记为 0、表格仍为 42 行，确认默认输出行为保持不变。
5. 回归输出保存在 `test_output/pdf-001-verification/`。

### 验证记录

- `cargo fmt --all -- --check`：通过。
- `cargo clippy --offline -- -D warnings`：通过，0 个 Clippy 警告。
- `cargo test --offline`：通过，共 864 项（718 项库单元测试、1 项命令测试、143 项集成测试、2 项文档测试），0 项失败。
- `cargo build --release`：通过。

### 全部测试集回归

修复后重新运行两批本地测试集，共 40 份、2,237 个已识别页面：

## 2. PDF-002：无文本页导致页面编号不连续

- 发现时间：2026-09-06
- 级别：中
- 状态：待确认并修复
- 影响模块：`src/markdown/convert.rs`、页面结果组装逻辑

### 现象

部分文件的物理页数大于 Markdown 页面标记数。缺少的页面可能是封面、空白页或纯图片页，但省略标记会使后续内容无法与原 PDF 页码稳定对应。

### 影响样本

1. 第一批 `18-large-print-novel.pdf`：282 页，只有 279 个标记，缺少第 1、4、6 页。
2. 第二批 `04-css-layout-sample.pdf`：13 页，只有 11 个标记，缺少第 2、4 页。
3. 第二批 `05-poetry-booklet.pdf`：208 页，只有 206 个标记，缺少第 2、185 页。

### 原因判断

页面标记目前更接近“有可输出文本的页面标记”，而不是“源 PDF 物理页面标记”。这会破坏引用页码、逐页对比和回归测试。

### 解决方案

1. 明确 `--pages` 的规则：为源文件的每个物理页面输出一个标记。
2. 无可提取文本时仍输出 `<!-- Page N -->`。
3. 可选地追加 `<!-- No extractable text -->` 或 `<!-- OCR required -->`，但不要改变页码。
4. 继续保持所有对外页码从 1 开始。

### 验收标准

1. 启用 `--pages` 时，标记数量等于 `page_count`。
2. 标记从 1 连续递增到 `page_count`，无重复、无缺号。
3. 纯图片页和空白页也保留页码位置。

## 3. PDF-003：多栏正文被误判为 Markdown 表格

- 发现时间：2026-09-06
- 级别：高
- 状态：待修复
- 影响模块：`src/tables/detect_heuristic.rs`、`src/extractor/layout.rs`、`src/markdown/convert.rs`

### 现象

报纸式、多栏式或左右对话式正文被转换成 Markdown 表格，造成句子断裂、阅读顺序错误和大量无意义单元格。

### 已确认样本

1. 第一批 `12-theatre-script.pdf` 第 3 页。
2. 第一批 `07-multicolumn-dictionary.pdf` 第 218、278、285、405 页。
3. 第一批 `18-large-print-novel.pdf` 第 27、105、152、252 页。
4. 第一批 `03-magazine-recast.pdf` 第 2 页输出了表格行。

### 原因判断

启发式表格检测对“多条竖向对齐的文本块”权重过高，没有充分区分表格、词典栏、戏剧角色对白、分栏小说和杂志正文。

### 解决方案

1. 在表格判定前先使用 newspaper/tabular 分类结果。
2. 对句子型文本增加否决条件，例如高标点密度、连续长句、跨行自然续写和段落缩进。
3. 要求候选表格至少有多行重复的列边界或明显的横纵分隔证据。
4. 对词典、戏剧和小说版式增加负样本回归测试。
5. 将启发式表格置信度写入调试日志，便于定位触发条件。

### 验收标准

1. 上述正文页不再生成 Markdown 表格。
2. 发票、税表、问卷和实际网格表格仍能正确输出。
3. 表格召回率不因修复出现明显下降。

## 4. PDF-004：检测器与转换器的表格判断不一致

- 发现时间：2026-09-06
- 级别：中
- 状态：待修复
- 影响模块：`src/detector.rs`、表格检测入口、Markdown 转换入口

### 现象

第一批 `03-magazine-recast.pdf` 的 `detect-pdf --analyze --json` 返回没有表格页，但 `pdf2md` 在第 2 页生成了 8 行 Markdown 表格。

### 原因判断

检测命令和转换命令可能使用了不同的表格检测条件、预处理结果或后处理回退路径。

### 解决方案

1. 将表格检测封装为共享结果，检测器和转换器消费同一个结构。
2. 如果转换阶段允许二次发现表格，应同步更新最终分析信息。
3. 增加断言：转换结果出现表格时，对应页面必须出现在最终 `pages_with_tables` 中。

### 验收标准

同一文件、同一组选项下，检测结果与最终转换采用的表格页集合一致。

## 5. PDF-005：正常词典文本被误判为需要 OCR

- 发现时间：2026-09-06
- 级别：高
- 状态：待修复
- 影响模块：`src/detector.rs`、garbage text 判定、语言字符统计

### 现象

第一批 `07-multicolumn-dictionary.pdf` 第 635、638 页存在可读的冰岛语词典正文，但检测结果将其标记为 `suspected_garbled_text` 并要求 OCR。

### 原因判断

乱码评分可能过度依赖 ASCII 字母数字比例。带重音的拉丁字母、词典缩写、音标、词条符号和多栏短文本降低了当前评分。

### 解决方案

1. 统计 Unicode 字母类别，而不只统计 ASCII 字母。
2. 将带重音拉丁字符、组合附加符号和常见词典标点计入有效文本。
3. 同时参考 ToUnicode 覆盖率、可打印字符比例和连续词形，而不是单一阈值。
4. 对接近阈值的页面比较原始字形数量与成功映射数量。
5. 将这两页加入固定回归测试。

### 验收标准

第 635、638 页不再被标记为 OCR，同时真正的扫描页仍然能够正确识别。

## 6. PDF-006：阿拉伯文 Type1 字体被解码成乱码

- 发现时间：2026-09-06
- 级别：高
- 状态：待修复
- 影响模块：`src/extractor/fonts.rs`、`src/tounicode.rs`、`src/text_utils.rs`

### 现象

第二批 `13-arabic-font-specimen.pdf` 检测和转换均返回成功，但 Markdown 中没有阿拉伯 Unicode 字符，反而出现 339 个 CJK 字符和 15 个“锟”字符。日志同时出现 `InvalidEncodingDifferenceGlyph`。

### 原因判断

Type1 `/Encoding /Differences` 中的 `uni0628.i` 等阿拉伯字形名称没有正确解析。回退过程可能把字符编码值按错误代码页解释，生成了看似有效但语义完全错误的 Unicode 字符。

### 解决方案

1. 优先使用有效的 ToUnicode CMap。
2. 支持 Adobe Glyph List 以及 `uniXXXX`、`uXXXXX` 字形名称解析。
3. 对 `.i`、`.f`、`.m`、`.isol` 等阿拉伯位置变体后缀先提取基础码点。
4. 未知字形不能通过本地代码页强制转成 CJK；应保留可诊断占位并设置编码问题标志。
5. 字符恢复后再执行 RTL/BiDi 排序与阿拉伯文字形处理。

### 验收标准

1. 输出包含正确的阿拉伯 Unicode 字符。
2. 不再出现由回退产生的无关 CJK 字符和“锟”字符。
3. `has_encoding_issues` 能准确反映无法恢复的字形。

## 7. PDF-007：合法的非零起始偏移 PDF 被拒绝

- 发现时间：2026-09-06
- 级别：高
- 状态：待修复
- 影响模块：PDF 文件头检查、`lopdf` 加载入口

### 现象

第二批 `20-pdf20-offset-start.pdf` 是 PDF Association 提供的合法 PDF 2.0 样本。文件在 `%PDF-2.0` 前包含说明文字。当前两个命令均拒绝该文件：

```text
detect-pdf exit 1
pdf2md exit 1
Not a PDF: file appears to be plain text
```

### 原因判断

当前入口只检查文件第 0 字节是否以 `%PDF-` 开头，没有在允许的前导区域查找 PDF 文件头。

### 解决方案

1. 在有限的前导字节范围内搜索第一个合法 `%PDF-x.y` 文件头。
2. 找到非零偏移后，从该位置创建解析缓冲区，再交给 `lopdf`，使交叉引用偏移以 PDF 数据起点为基准。
3. 保留对 HTML、文本错误页和伪造文件的拒绝逻辑。
4. 同时测试标准文件头、非零偏移和增量保存文件。

### 验收标准

1. 该样本可被检测并转换。
2. 第二批 `19-pdf20-incremental-save.pdf` 继续通过。
3. 普通文本文件仍返回清楚的非 PDF 错误。

## 8. PDF-008：特殊字形产生大量重复警告

- 发现时间：2026-09-06
- 级别：中
- 状态：待修复
- 影响模块：字体解析日志、编码回退

### 现象

第二批 `09-historical-essay.pdf` 虽然成功转换 408 页，但日志反复输出 `InvalidEncodingDifferenceGlyph`，并附带体积很大的完整字体字典。主要涉及 `long s`、连字和 swash 字形。

### 风险

1. 大量重复日志掩盖真正错误。
2. 特殊字形虽然没有生成 U+FFFD，仍可能被错误替换或丢失。
3. 批量测试日志体积和处理成本增加。

### 解决方案

1. 按“字体对象 + 字形名”去重警告。
2. 日志只输出字体名、对象号、字形名和回退策略，不打印完整字体字典。
3. 扩充常见历史字形、连字和 swash 字形映射。
4. 在调试级别保留完整对象信息，默认警告级别输出汇总。

### 验收标准

1. 相同字体和字形最多产生一次警告或一条汇总。
2. 抽样核对历史字形，确认文字没有丢失或错误替换。
3. JSON 标准输出保持纯净，诊断信息只写入标准错误流。

## 9. PDF-009：仅检查 U+FFFD 无法发现全部乱码

- 发现时间：2026-09-06
- 级别：中
- 状态：待补充测试
- 影响模块：本地回归测试和输出质量检测

### 现象

两批输出的 U+FFFD 计数均为 0，但阿拉伯文样本仍产生大量错误的 CJK 字符。这说明“没有替换字符”不等于“文本解码正确”。

### 解决方案

1. 增加按 Unicode Script 分类的字符统计。
2. 将 PDF 字体、ToUnicode 或字形名称推断出的主要文字脚本与输出脚本进行比较。
3. 增加常见乱码模式检查，例如“锟”、异常控制字符和与文档语言无关的大量字符。
4. 为已知语言样本保存最小语义断言，例如输出至少包含一定数量的阿拉伯字母。
5. 保留人工抽样检查，避免自动指标把合法的多语言内容误报为乱码。

### 验收标准

1. 当前阿拉伯文样本能够被自动质量检查判定为失败。
2. 中英双语表单不会因为同时出现中文和英文而误报。
3. 普通英文、冰岛语和 RTL 样本分别具有独立的合理性规则。
