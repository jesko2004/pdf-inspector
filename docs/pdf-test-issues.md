## 1. PDF-001：表格内容页缺少页面标记

- 发现时间：2026-09-06
- 修复时间：2026-09-06 16:30:47（Asia/Shanghai）
- 级别：高
- 状态：已关闭（实现完成并通过真实样本回归）
- 影响模块：`src/markdown/convert.rs`、表格输出与页面分组逻辑

### 现象

启用 `pdf2md --pages` 后，部分页面的内容已经写入 Markdown，但对应的 `<!-- Page N -->` 标记没有写入。

### 已确认样本

1. 第一批 `13-tax-return-form.pdf`：源文件共 2 页，第 2 页内容存在于一个大型 Markdown 表格中，但缺少 `<!-- Page 2 -->`。
2. 第二批 `02-full-product-catalogue.pdf`：源文件共 4 页，输出标记为 `1、2、4`；检测器确认第 3 页有表格，输出也包含该页商品表格，因此第 3 页不是空白页。

### 原因判断

表格可能通过独立于普通文本行的输出分支写入。页面标记由普通文本循环触发时，只有表格或者由跨页表格承载内容的页面不会触发标记。

### 解决方案

1. 将 Markdown 生成过程统一成“按源 PDF 页逐页输出”。
2. 每一页开始时先写页面标记，再写该页的表格、正文、图片提示等内容。
3. 表格检测结果应携带原始页码，跨页表格也要在页边界插入对应标记。
4. 避免由“该页是否存在普通 TextLine”决定是否写页面标记。

### 实际修复方法

1. 为 `merge_continuation_tables` 增加 `preserve_page_boundaries` 参数。
2. 当 `MarkdownOptions.include_page_numbers` 为 `true` 时，不再把后续表格页合并并删除，而是保留每一页的表格数据和原始页码。
3. 刷新位于两个正文页之间的 table-only/image-only 页面前，先输出该页的 `<!-- Page N -->` 标记。
4. 刷新最后一个正文页之后剩余的 table-only/image-only 页面时，同样先输出页面标记。
5. 未启用 `--pages` 时仍按原有逻辑合并跨页连续表格，避免改变默认 Markdown 输出策略。
6. 新增两个单元测试，分别验证中间表格页的标记顺序，以及启用页面标记时连续表格页不会被合并删除。

### 验收标准

1. 上述两份样本的标记序列分别严格为 `1,2` 和 `1,2,3,4`。
2. 每个标记只出现一次。
3. 修复后表格内容和阅读顺序不发生倒退。

### 修复结果

1. `13-tax-return-form.pdf`：修复前只有 `Page 1`，修复后标记严格为 `1,2`，42 行 Markdown 表格仍然保留。
2. `02-full-product-catalogue.pdf`：修复前标记为 `1,2,4`，修复后严格为 `1,2,3,4`，第 3 页商品表格仍然保留。
3. 两份样本的 `pdf2md` 退出码均为 0。
4. 不使用 `--pages` 再次转换报税表时，页面标记为 0、表格仍为 42 行，确认默认输出行为保持不变。
5. 回归输出保存在 `test_output/pdf-001-verification/`。

## 2. PDF-002：无文本页导致页面编号不连续

- 发现时间：2026-09-06
- 修复时间：2026-09-07 17:27:00（Asia/Shanghai）
- 最终复核时间：2026-09-07（Asia/Shanghai）
- 级别：中
- 状态：已关闭（实现完成并通过真实样本回归）
- 影响模块：`src/lib.rs`、`src/markdown/mod.rs`、`src/markdown/convert.rs`、页面结果组装逻辑

### 现象

部分文件的物理页数大于 Markdown 页面标记数。缺少的页面可能是封面、空白页或纯图片页，但省略标记会使后续内容无法与原 PDF 页码稳定对应。

### 影响样本

1. 第一批 `18-large-print-novel.pdf`：282 页，只有 279 个标记，缺少第 1、4、6 页。
2. 第二批 `04-css-layout-sample.pdf`：13 页，只有 11 个标记，缺少第 2、4 页。
3. 第二批 `05-poetry-booklet.pdf`：208 页，只有 206 个标记，缺少第 2、185 页。

### 已确认原因

Markdown 转换器只能看到包含文本、表格或已输出图片的页面，没有接收到源 PDF 的物理页数。它会为已有内容切换页面并生成标记，但无法知道两个内容页之间或文档首尾还存在空白页、纯图片页或无可提取文本页。最终复核还发现，上层 Markdown 组装函数会在文本项为空时提前返回，使整份无文本 PDF 无法进入页面标记生成流程。

### 已实施修复

1. 主处理链路将加载 PDF 时得到的 `page_count` 传入 Markdown 页面输出上下文。
2. 启用 `--pages` 时，转换器按物理页码补写内容页之间、首部和尾部缺失的 `<!-- Page N -->`。
3. 表格页和图片页继续通过原有刷新流程输出内容，补齐标记不会复制或移动其内容。
4. 未启用 `--pages` 时保持原有 Markdown 输出；独立的公共 Markdown 组装 API 也不推测未知物理页数。
5. 使用内部上下文结构传递页阈值、页面分割集合和物理页数，避免扩大公开配置结构或产生参数膨胀。
6. 增加中间空页、首尾空页和全部无文本项的单元测试。
7. 调整上层空输入判断：当启用 `--pages` 且已知物理页数时，即使文本项为空也继续组装 Markdown，确保整份空白或纯图片文档仍保留连续页面标记。

### 修复结果

1. `18-large-print-novel.pdf`：页面标记由 279 个增至 282 个，序列严格为 1 至 282，补齐第 1、4、6 页。
2. `04-css-layout-sample.pdf`：页面标记由 11 个增至 13 个，序列严格为 1 至 13，补齐第 2、4 页。
3. `05-poetry-booklet.pdf`：页面标记由 206 个增至 208 个，序列严格为 1 至 208，补齐第 2、185 页。
4. 40 份本地 PDF 全量回归中，37 份直接转换文件的标记数全部等于物理页数，0 份存在缺号或重复；3 份整文件 OCR 样本仍按预期进入 OCR，0 份被拒绝。
5. Markdown 总字符数由 4,328,894 增至 4,329,015，增加的 121 个字符均来自补齐的 7 个页面标记；U+FFFD 保持 381 个，表格行数保持 647 行。
6. 新增入口级边界测试，确认两页且无任何文本项的文档仍输出 `<!-- Page 1 -->` 和 `<!-- Page 2 -->`。

### 验证记录

- `cargo fmt --all -- --check`：通过。
- `cargo clippy --offline -- -D warnings`：通过，0 个 Clippy 警告。
- `cargo test --offline`：通过，共 879 项（731 项库单元测试、1 项命令测试、145 项集成测试、2 项文档测试），0 项失败。
- `cargo build --release --offline`：通过。

## 3. PDF-003：多栏正文被误判为 Markdown 表格

- 发现时间：2026-09-06
- 修复时间：2026-09-06 23:08:00（Asia/Shanghai）
- 级别：高
- 状态：已关闭（实现完成并通过真实样本回归）
- 影响模块：`src/tables/detect_heuristic.rs`、`src/tables/detect_lines.rs`、`src/markdown/mod.rs`

### 现象

报纸式、多栏式或左右对话式正文被转换成 Markdown 表格，造成句子断裂、阅读顺序错误和大量无意义单元格。

### 已确认样本

1. 第一批 `12-theatre-script.pdf` 第 3 页。
2. 第一批 `07-multicolumn-dictionary.pdf` 第 218、278、285、405 页。
3. 第一批 `18-large-print-novel.pdf` 第 27、105、152、252 页。
4. 第一批 `03-magazine-recast.pdf` 第 2 页输出了表格行。

### 原因判断

启发式表格检测对“多条竖向对齐的文本块”权重过高，没有充分区分表格、词典栏、戏剧角色对白、分栏小说和杂志正文。

### 解决方案

1. 在表格判定前先使用 newspaper/tabular 分类结果。
2. 对句子型文本增加否决条件，例如高标点密度、连续长句、跨行自然续写和段落缩进。
3. 要求候选表格至少有多行重复的列边界或明显的横纵分隔证据。
4. 对词典、戏剧和小说版式增加负样本回归测试。
5. 将启发式表格置信度写入调试日志，便于定位触发条件。

### 验收标准

1. 上述正文页不再生成 Markdown 表格。
2. 发票、税表、问卷和实际网格表格仍能正确输出。
3. 表格召回率不因修复出现明显下降。

### 实际修复方法

1. 扩展段落否决规则，识别稀疏中间锚点、短单词碎片、两行引文和密集多栏长句，避免仅凭 X 坐标对齐生成启发式表格。
2. 线框检测仅在候选网格填充密度较高且单元格呈持续长句时拒绝候选；低密度填写表单继续保留，避免空白填写区被当作正文。
3. 对仅占页面一部分但结构自身完整的双列标签表格放宽页面覆盖率限制；要求至少 3 行、每行两列基本填满且每个非空单元格均有匹配文本。
4. 新增 7 个定向单元测试，覆盖四类正文误判、带数据的稀疏真表格、完整双列标签表和不完整标签结构。
5. 使用原始 PDF 页面渲染核对杂志、OSHA 说明页、W-9 双列表和香港预算表，防止仅根据 Markdown 行数判断结果。

### 修复结果

1. 10 个已登记误判页全部不再生成 Markdown 表格：戏剧第 3 页；词典第 218、278、285、405 页；小说第 27、105、152、252 页；杂志第 2 页。

3. W-9 第 3、4、5 页的完整双列表按标签结构输出，第 5 页两张表不再吸收旁边的身份盗用说明；该文件的正确表格行由旧的 12 行改善为 34 行。
4. 香港预算表第 28 页继续保留 5 行 Markdown 表格；发票、报税表、问卷和其他网格表格的定向检查通过。
5. 完整 40 份回归结果：40 份检测成功，37 份直接转换，3 份进入 OCR，0 份被拒绝；输出 4,328,894 个字符，U+FFFD 为 381 个，全部来自既有的香港双语表单问题。

## 4. PDF-004：检测器与转换器的表格判断不一致

- 发现时间：2026-09-06
- 修复时间：2026-09-07（Asia/Shanghai）
- 级别：中
- 状态：已关闭（目标样本复测一致）
- 影响模块：`src/detector.rs`、表格检测入口、Markdown 转换入口

### 现象

第一批 `03-magazine-recast.pdf` 的 `detect-pdf --analyze --json` 返回没有表格页，但 `pdf2md` 在第 2 页生成了 8 行 Markdown 表格。

### 已确认原因

目标样本第 2 页的多栏正文曾在 Markdown 阶段触发启发式表格误判，而布局分析没有把该候选识别为数据表，因此出现元数据与输出不一致。该候选属于 PDF-003 的多栏正文误判，不是真实表格。

### 已实施修复

1. PDF-003 修复增加了平行正文候选拒绝规则，使布局分析和 Markdown 转换都不再把该页识别为表格。
2. 保留 `pages_with_tables` 仅表示数据表的规则，目录和多栏正文不进入表格页集合。
3. 对目标文件同时运行 `detect-pdf --analyze --json` 和 `pdf2md --pages`，直接比较分析结果与 Markdown 表格行。

### 修复结果

`03-magazine-recast.pdf` 检测和转换均成功；`pages_with_tables` 为空，Markdown 表格行为 0，第 2 页不再出现 8 行伪表格。该目标样本的检测结果与最终输出一致。

1. 将 Latin-1 范围内的字母与符号分别统计；高比例的重音字母不再单独构成乱码证据。
2. 高 Latin-1 比例分支现在还要求至少出现 3 个 Latin-1 非字母数字符号，才判定为字节级 CID mojibake。
3. 保留原有 C1 控制字符、私用区、替换字符、非字母数字符号汤和移位乱码检测。
4. 增加第 635、638 页真实词条对应的单元回归，并补充无 C1 控制字符的符号型 Latin-1 乱码保护测试。

## 6. PDF-006：阿拉伯文字形映射不完整并产生重复警告

- 发现时间：2026-09-06
- 修复时间：2026-09-06 17:00:05（Asia/Shanghai）
- 级别：高
- 状态：已关闭（实现完成并通过真实样本回归）
- 影响模块：`src/glyph_names.rs`、`src/tounicode.rs`、`src/extractor/fonts.rs`、字体编码缓存

### 现象

第二批 `13-arabic-font-specimen.pdf` 检测和转换均返回成功，但 Markdown 中仍有 15 个 U+FFFD 替换字符。日志同时重复出现 `InvalidEncodingDifferenceGlyph`，涉及 `uni0628.i` 等带阿拉伯位置变体后缀的 Type1 字形名。

早期统计曾报告 0 个阿拉伯字符、339 个 CJK 字符和 15 个“锟”字符。复核文件原始 UTF-8 内容后确认，这是 PowerShell `Get-Content` 未指定 `-Encoding UTF8` 导致的测试脚本误读；修复前的实际输出包含 274 个阿拉伯字符、0 个 CJK 字符、0 个“锟”字符和 15 个 U+FFFD。后续字符统计均显式使用 UTF-8。

### 原因判断

1. 字形解析器能去掉 `.i`、`.f`、`.m`、`.isol` 等后缀，但去掉后缀后只查询固定字形表，没有继续解析 `uniXXXX` 和 `uXXXXX` 码点。
2. Type0 内嵌 TrueType 字体的标准 cmap 没有覆盖部分阿拉伯变体字形；这些 GID 的 `post` 字形名仍包含可恢复的 Unicode，例如 `uni0634.fina.alt`。
3. 大型 ToUnicode CMap 即使包含大量 U+FFFD，也因条目数充足而不会建立内嵌字体回退映射。
4. lopdf 会再次解析已经由项目自定义逻辑处理的 Differences 字典，产生重复且体积较大的警告。

### 解决方案

1. 字形名称去掉点号后缀后，继续执行 Adobe Glyph List、`uniXXXX` 和 `uXXXXX` 解析。
2. 反转内嵌 TrueType cmap 后，再用 `post` 字形名补齐尚未映射的 GID；已有 cmap 映射仍保持最高优先级。
3. ToUnicode 出现空值或 U+FFFD 时建立内嵌字体回退，并逐个 CID 使用回退值修复无效主映射，避免替换同一文本操作数中的正确主映射。
4. 已建立自定义 Differences 映射的字体不再交给 lopdf 重复解析，消除 `InvalidEncodingDifferenceGlyph` 警告。
5. 新增 `uni0628.i` 等后缀字形解析测试，以及“只修复无效 CID、保留有效主映射”的单元测试。

### 验收标准

1. 输出包含正确的阿拉伯 Unicode 字符。
2. U+FFFD、无关 CJK 字符和“锟”字符均为 0。
3. `InvalidEncodingDifferenceGlyph` 重复警告为 0。
4. 页面数量、页面标记和已有拉丁文字内容保持完整。

### 修复结果

1. `13-arabic-font-specimen.pdf` 转换退出码为 0，5 个页面标记完整保留。
2. 阿拉伯字符从 274 个增加到 331 个。
3. U+FFFD 从 15 个降到 0；CJK 字符和“锟”字符均保持为 0。
4. `InvalidEncodingDifferenceGlyph` 警告从 2 次降到 0。
5. 修复前后的 UTF-8 输出和日志保存在 `test_output/pdf-006-verification/`，由 Git 忽略，不进入仓库。

## 9. PDF-009：仅检查 U+FFFD 无法发现全部乱码

- 发现时间：2026-09-06
- 修复时间：2026-09-07（Asia/Shanghai）
- 级别：中
- 状态：已关闭（自动质量检查已补充并通过目标样本）
- 影响模块：本地回归测试和输出质量检测

### 现象

两批输出的 U+FFFD 计数均为 0，但阿拉伯文样本仍产生大量错误的 CJK 字符。这说明“没有替换字符”不等于“文本解码正确”。

### 已确认原因

U+FFFD 只能反映解码器明确失败的字符。错误码点如果仍是合法 Unicode，例如阿拉伯字形被错误映射为 CJK，替换字符计数仍为 0，因此需要结合预期文字脚本和异常字符模式判断。

### 已实施修复

1. 新增 `scripts/check_text_quality.py`，使用 Python 标准库统计 Latin、Arabic、Han、Hebrew、Cyrillic 和 Devanagari 字母。
2. 支持 `--expect-script`、`--forbid-script` 和最少字符数门槛，用样本语言预期发现“合法 Unicode 但脚本错误”的静默乱码。
3. 同时检查 U+FFFD、C1 控制字符、私用区字符和高置信度 mojibake 片段；各阈值可按已知样本基线配置。
4. JSON 报告写入标准输出，并以退出码 0/1 表示通过或失败，便于加入批量回归。
5. 新增 4 项 Python 单元测试，覆盖阿拉伯文被 CJK 替换、正常阿拉伯文、中英双语和异常字符。

### 修复结果

1. 阿拉伯样本自动统计 405 个 Arabic 字母、765 个 Latin 字母、0 个 Han 字母、0 个 U+FFFD，质量门禁通过；修复前“Arabic 为 0、Han 大量出现”的输出会被两条规则同时拒绝。
2. 历史英文样本统计 265,132 个 Latin 字母，U+FFFD、C1 控制字符、私用区字符和 mojibake 标记均为 0，质量门禁通过。
3. 中英双语表单统计 6,768 个 Han 字母和 34,484 个 Latin 字母，脚本组合被正确接受；其既有 381 个 U+FFFD 和 5 个 C1 控制字符可通过独立阈值持续跟踪，不会因中英混合本身误报。
4. `python -m unittest scripts.tests.test_check_text_quality`：4 项通过，0 项失败。

### 使用方式

```bash
python scripts/check_text_quality.py output.md \
  --expect-script arabic \
  --forbid-script han \
  --min-script-characters 50 \
  --max-replacement-characters 0
```

命令输出 JSON；`status` 为 `pass` 时退出码为 0，发现脚本缺失、禁用脚本或异常字符超限时退出码为 1。
